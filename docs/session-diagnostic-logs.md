# 会话诊断日志实时追加

当前 schema 16 的 `session.jsonl` 是会话回放和 Run 终态的数据源。模型适配器、执行器等组件产生的会话级诊断事件写入独立的 `<session_id>.jsonl`。排查时可以用 `run_id` 从会话终态定位到同一轮的诊断事件。日志写入和 TOS 上传由诊断链路负责，上传结果独立于 Run 终态、工作区快照和会话记录提交。

## 对象与记录格式

TOS 使用同一个会话目录。宿主在 `<runtime.workspace_temp_root>/.sessions/` 下使用相同的相对路径保存诊断日志。

```text
<prefix>/<space_id>/sessions/<session_id>/
  session.jsonl
  <session_id>.jsonl
```

诊断日志使用 UTF-8 JSONL，每条记录以换行结束，字段固定如下。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `timestamp` | string | 事件发生时间，使用 UTC RFC 3339 |
| `level` | string | 日志级别，如 `warn` 或 `error` |
| `event` | string | 由事件产生方定义的稳定事件名 |
| `run_id` | string 或 null | 所属 Run 的 ID。会话级事件填 `null` |
| `msg` | string | 供排查使用的简明说明 |

日志只记录诊断值，模型响应正文、凭证和工具载荷由各自的现有路径处理。

以下事件仅作格式示例。

```jsonl
{"timestamp":"2026-11-17T14:49:14.721Z","level":"warn","event":"model.attempt_failed","run_id":"bbbbbbbbbbbbbbbb","msg":"attempt_id=example purpose=task stage=stream http_status=200"}
```

## 首版日志清单

日志要支持两类排查。运行中能定位最后进入的阶段和正在调用的组件。运行失败后，能把终态错误码追溯到具体操作、错误原因和触发门限。`session.jsonl` 提供已归档的模型步骤、工具结果和终态，诊断日志提供实时进度及这些记录缺失的失败细节。以下各项所需的诊断值都写进 `msg`。

### 运行中的进度

| `event` | 记录时机 | `msg` 至少记录 |
| --- | --- | --- |
| `run.claimed` | 调度器成功认领 Run | 从接受到认领的等待时间 |
| `model.attempt_started` | 模型网关发起一次实际模型调用前 | `attempt_id`、用途（任务或摘要）。发生重试时记录前一次尝试 ID |
| `tool.execution_started` | 工具参数校验通过，即将执行工具时 | 工具名和 `call_id` |
| `run.finalizing` | 进入 Run 收尾，开始处理快照及会话持久化 | 当时的执行结果、是否进入快照保存 |

进度事件用 `info`。等待或卡住时，用最后一条进度记录确定 Run 已进入的阶段，再结合运行状态或实时 Trace 判断当前进展。

### 失败原因

| `event` | 记录位置与条件 | `msg` 至少记录 |
| --- | --- | --- |
| `run.start_failed` | 调度拒绝该 Run，或启动检查、执行器初始化失败时 | 阶段和实际错误码。已取得的超时门限或 MariaDB 错误码一并记录 |
| `run.interrupted` | 执行中收到取消、撤权、执行期限或服务停止信号，或重启时将遗留 Run 判为中断 | 已确认的触发原因。重启恢复只记录恢复时观测到的 Run 状态，有证据时再注明退出原因 |
| `context.prepare_failed` | 在发出模型请求前，上下文历史读取、投影或摘要准备失败时 | 阶段和错误码。输入超限时记录估算输入、有效输入上限和预留输出 |
| `run.limit_exceeded` | Run 控制器或执行循环拒绝继续执行时 | 实际命中的限制，如模型调用次数、工具调用次数、累计 Token 预算或执行时间，以及当时的计数和门限 |
| `model.attempt_failed` | 模型凭证解析、请求、流读取或协议校验失败时，在返回通用错误码前记录 | `attempt_id`、失败阶段和分类后的实际错误。已收到 HTTP 状态或供应商请求 ID 时一并记录 |
| `tool.execution_failed` | 工具失败将中止 Run、被归并为通用 `tool_failed`，或被判为 `side_effect: unknown` 时 | 工具名、`call_id`、失败阶段、可确认的错误原因和副作用分类。工具结果超限时记录实际字节数和门限 |
| `tool.network_request_failed` | 代码工具内的 HTTP 请求未能取得可用响应时 | `call_id`、请求序号、方法、主机名、阶段、分类后的错误和副作用。工具结果中的 `network_failure` 保留最近一次失败的这些信息，投影截取长结果时仍会传给模型 |
| `workspace.operation_failed` | 工作区恢复、文件写入配额检查、快照打包、归档上传、清单保存或快照提交失败时 | 操作阶段和实际错误码。工作区超限时在检查点记录参与归档的累计字节、触发条目的字节数和有效上限 |
| `session.persist_failed` | 保存 `session.jsonl`、上传会话对象或更新 Run 终态索引失败时 | 失败环节、本次需要提交的会话记录位置，以及可取得的存储或数据库错误码 |

同一个异常在能取得原始诊断值的边界记录一次。文件工具遇到工作区总量超限由 `workspace.operation_failed` 说明。摘要模型调用失败也按同一模型事件记录，借助日志中的用途区分。正常的工具拒绝、工具输出和成功结果沿用实时 Trace 与会话记录。未知的状态码、计数或故障原因直接省略。诊断日志自身的落盘或追加失败写入服务日志，避免再次进入会话日志上传链路。

排查时用 `run_id` 找到最后的进度记录和异常。遇到 `context_overflow`，用 `context.prepare_failed` 或 `tool.execution_failed` 确定出错位置。旧版本的 `model.stream_limit_exceeded` 记录原 Eino 适配器的分片数或分片序列化字节数超限。遇到 `workspace_snapshot_failed`，用工作区事件区分打包超限、上传失败和提交失败。宿主已有终态而远端只看到接收记录时，用 `session.persist_failed` 或宿主服务日志定位持久化问题。

## 本地追加与异步提交

1. 事件产生时，将完整日志行按会话串行追加并持久化到宿主文件，然后立即唤醒后台任务。宿主文件中本地确认位置之后的完整行就是待上传队列。后台任务使用服务生命周期的上下文发起 TOS 请求，Run 无需等待网络响应。同一对象同一时间只发送一批，队列中已有的多条完整日志可以合并发送。
2. 复用现有 Go SDK 的 `AppendObjectV2`。首次写入以 `offset=0` 创建标准存储的可追加对象，内容类型为 `application/x-ndjson`。既有对象的初始偏移通过 `HeadObject` 获取，只有确认对象不存在时才使用 `0`。后续使用成功响应的 `x-tos-next-append-offset`。偏移是对象字节数，包含每行末尾的换行。发送时只带本批新增行。[TOS AppendObject 文档](https://docs.volcengine.com/docs/torch-object-storage/append-object?lang=zh)
3. 发送前在宿主持久化该批的远端目标偏移和本地字节范围。重试从本地日志读取该范围的原始字节。成功后持久化本地确认位置，后续只消费未确认的行。上传状态与日志记录分开保存。后台任务独立于 `session.jsonl` 的上传时机运行，写入资格复用当前部署的运行租约。

## 超时、进程重启与换宿主

收到超时、响应丢失或偏移冲突时，对同一批执行核对。设 `offset` 为该批起始偏移，`size` 为待发送的字节数。

| 远端状态 | 处理 |
| --- | --- |
| 对象长度等于 `offset`，或首次追加时确认对象尚不存在 | 使用原偏移重试同一批字节 |
| 对象长度至少为 `offset + size` | 读取 `[offset, offset + size)` 的字节范围。与本地批次完全一致时确认该批成功，后续从远端末尾续写 |
| 对象长度异常，或该范围的内容与待发送批次不同 | 保留待发送批次，记录偏移冲突，暂停该会话后续追加 |
| 远端查询或读取暂时失败 | 保留待发送批次，由后台重试核对 |

同一宿主重启时恢复待上传队列，对可能已提交的批次先核对远端状态，再继续追加。换宿主时从 TOS 上已确认的字节位置续写。尚未上传的记录仍在原宿主的队列中。日志写入或上传失败通过服务日志暴露，Run 按原有执行路径收尾。

## 查询与验收

新增 `GET /api/v1/diagnostic-logs`，沿用现有诊断入口的 Cookie 鉴权、空间成员检查和 ID 定位方式。请求在 `session_id` 与 `run_id` 中传且仅传一个。前者下载该会话已上传的诊断日志，后者只返回 `run_id` 匹配的记录。响应直接返回 `application/x-ndjson`。已有会话从第一条新诊断事件开始创建对象，在首次上传前返回空 JSONL。

- Run 还在执行时，已产生的诊断日志可通过下载接口从 TOS 读取。后续追加保留历史行，并维持同一会话的追加顺序。
- 模拟 TOS 已写入但客户端丢失响应，验证范围核对确认同一批，远端只出现一次该批日志。覆盖同宿主重启后恢复待上传批次的情况。
- 换宿主后从远端偏移继续追加，保留此前已经确认上传的记录。日志上传故障时，Run 仍能按原有流程提交终态。
- 按 `run_id` 能看出 Run 停在模型调用、工具执行还是收尾。用失败夹具分别验证模型请求前输入超限、模型响应分片数或字节数超限（含两者同时命中）、只返回通用错误的工具失败、工作区超限以及会话上传失败。每种情况都能从 `event` 和 `msg` 找到实际失败环节与已取得的诊断值。
